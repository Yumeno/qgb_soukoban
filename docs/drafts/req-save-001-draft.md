# REQ-SAVE-001 検討ドラフト(issue #1 対応)

- 状態: 改訂版(Codex レビュー全指摘採用 2026-07-12)。次工程で REQ-SAVE-001 として scaffold する
- 対象 issue: https://github.com/Yumeno/qgb_soukoban/issues/1

## 1. なぜ新 REQ が必要か

issue #1 の機能群は「**利用者の保存データを壊さない**」という約束を初めて導入する:

- 保存スキーマが v1 → v2 に変わる(視聴フラグ・ランダム履歴の追加)
- 現行実装は「版不一致は初期化」なので、**このまま出すと既存プレイヤーのクリア記録が全消滅する**
- リセット2系統は破壊的操作であり、「消すべきものだけ消す」選択性が約束になる

これは既存 3 REQ(CORE=ルール、SOLV=可解性、DIST=配布物)のどれにも属さない persistence の約束。機械検査可能(単体テスト)なので REQ 化に適する。

## 2. REQ-SAVE-001 案

- **守りたい約束**: 保存された記録は参照先の盤面と常に整合し、初期化操作は宣言した範囲だけを消す
- **stages**: S1-static, S2-unit(新しい段階は不要)
- **現行 v1 データの扱い(2026-07-12 ユーザー判断)**: v1 データは「ステージ再生成のたびに不整合になっている」ため**破棄してよい**(移行処理は実装しない)。代わりに恒久対策として、v2 の記録を**盤面内容に紐付ける**。

### acceptance criteria(テストケース対応。改訂版)

1. **盤面ハッシュ紐付けと選択的失効**: v2 の各ステージ記録は盤面ハッシュ(stage text の sha-256 等)を保持し、ロード時に現行 STAGES の盤面とハッシュ不一致の記録は**その記録だけ**無効化される。他の記録・`solutionViewed`・ランダム履歴は保持する(選択的失効。全消去にしない)。
2. **ランダム履歴の整合検証**: ランダム履歴のエントリは seed+params から再生成した盤面と整合することを検証してから表示に使う。再生成失敗・不一致エントリは表示から除外する(選択的除外。他エントリに影響しない)。
3. **異常系の安全な扱い**: v1 データ・壊れた JSON・未知版は安全に初期状態を返す(throw しない)。
4. **保存失敗の意味論**(レビュー指摘 1): `localStorage.setItem` が失敗した場合、
   - 失敗は呼び出し元(UI 層)へ返る(黙って握り潰さない)
   - 失敗時に既存の保存データを意図的に消さない(書き込み前のデータをそのまま保持する)
   - UI はユーザーに保存不能状態を表示する(無言で失われたことにしない)
5. **リセット2系統の意味論**(レビュー指摘 2):
   - `resetClearRecords`(クリア記録のみ消去): `solutionViewed` を保持する。ランダム履歴の存在も保持する。
   - `clearAllProgress`(完全初期化): クリア記録・`solutionViewed`・ランダム履歴のすべてを消去する。
   - **特典(査定ランクの `cappedByViewing` 上限解除)は `clearAllProgress` のみが解除する**。`resetClearRecords` では解除されない。この非対称は仕様であり AC として固定する。
   - 別操作 `clearSolutionViewed`(視聴履歴だけを選択的に消す第 3 の操作)の新設は今回のスコープでは見送る。将来要望として issue #1 に代替案を記録済み扱いとする。
6. **査定上限の機械検査可能化**(レビュー指摘 3): `solutionViewed === true` の面(収録面・ランダム面のいずれも対象)は、最短手数(`moves === minMoves`)でクリアしても査定ランクは「優」ではなく「A」(`grade: "A"`, `cappedByViewing: true`)を返す。`solutionViewed === false` の面は最短手数で「特(S)」を返す。この上限規則は収録面・ランダム面の両方に同一のロジックで適用される。
7. **模範解の由来の明確化**(レビュー指摘 4): 収録面・ランダム面プールの `optimalSolution` は**いずれもソルバー(move-BFS)由来の最短解**である。生成器が構成時に持つ「証明解」(逆押し pull から構成された解、必ずしも最短ではない)とは別物であり、収録・配布データとしては採用しない。AC は「`optimalSolution` を初期盤面に適用すると勝利到達 && その手順長 `=== ` ソルバー再計算 `minMoves`」。
8. **保存キー戦略**(レビュー指摘 5): v2 は新しい localStorage キー `qgb-soukoban/v2` を使う。v1 キー(旧実装のキー)は**読まず、消さず、放置する**(破壊しない原則。移行もクリーンアップも行わない)。
9. **確認 UX**(レビュー指摘 6):
   - `resetClearRecords` は確認 1 段(「クリア記録を削除します」等の単段確認)。
   - `clearAllProgress` は確認 2 段階とし、文言に「模範解の視聴履歴・ランダム履歴も削除します」を含める(1 段目の説明文言または 2 段目の再確認文言のいずれかに明記していればよい)。
10. `mergeClearRecord` / `recordRandomPlay` はいずれも `solutionViewed` を破壊しない(既存フラグを保持したまま該当フィールドのみ更新する)。
11. (将来の約束・スコープ外)v2 以降の版移行は無損失で行う。今回は v1→v2 の移行を実装しないため対象外。

## 3. REQ-SOLV-001 への追記(模範解真正性)

- acceptance criteria に追加: **模範解の真正性** — 焼き込み `optimalSolution` が (a) 適用で勝利到達 (b) 長さ `===` `minMoves`(=本当に最短、ソルバー再計算値と一致)。収録面(T-13)とシードプール(SP-05)の両方が対象。ソルバー由来の最短解であることを明示し、生成器の構成的証明解とは区別する(上記 §2-7 と対応)。
- S3(`tools/verify-stages.mjs`)の検査項目に `optimalSolution` の再検証を追加する:
  - 収録面: **全数**(per-stage 表に `optLen==minMoves` 列を追加)
  - ランダム面プール: 全数検証はビルド時に行うため、S3 では各難易度から**固定 10 エントリ**を抽出して同様に検査する(実行時間との折り合い。全数はビルドパイプライン側の責務)

## 4. contract への影響

- 既存 contract のコマンドは変更不要(S2 は node --test で新テストを自動的に包含、S3 は verify-stages の内部拡張)
- REQ-SAVE-001 の contract: S1 は既存と同一(`node tools\check-syntax.mjs`)、S2 は `node --test`(いずれも実績ある形の再利用)
