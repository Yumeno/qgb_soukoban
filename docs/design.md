## 1. 目的と要件

ブラウザで動作する絵文字グリッドグラフィックの倉庫番ゲームを TDD で開発する。品質保証は qgb (quality-gate-builder) の機械ゲートで担保する。

### 機能要件

| ID | 要件 |
|---|---|
| F-01 | 倉庫番の標準ルール(移動・箱押し・全箱ゴールで勝利)で遊べる |
| F-02 | 生成選抜 10 ステージ(逆押し生成器の候補群から難易度カーブに沿って選抜し焼き込み) |
| F-03 | ランダム生成モード(生成された面もクリア可能性を保証) |
| F-04 | undo(多段。1 手ずつ巻き戻し)とリセット |
| F-05 | ステージ選択メニュー + クリア記録の永続化 (localStorage) |
| F-06 | 歩数カウント + そのステージの最短手数の表示 |
| F-07 | クリア時のリプレイ記録と再生 |
| F-08 | 絵文字グリッドグラフィック(固定サイズセルの CSS グリッド + 絵文字、ゴールは CSS 破線枠) |
| F-09 | 査定ランク(クリア時の歩数を最短手数と比較し特/優/良/可の4段階で判定。ランダム面にも適用。§8 参照) |

### 非機能要件

| ID | 要件 |
|---|---|
| NF-01 | vanilla HTML/CSS/JS。ビルド工程なし、npm 依存ゼロ |
| NF-02 | コアロジックは DOM 非依存の純粋 ESM とし、node:test (Node 22 組込) で単体テスト可能 |
| NF-03 | 収録 10 面は全数ソルバー検証でクリア可能性を担保。ランダム生成面は構成的保証(合法 push の逆写像)+ 固定シード代表集合の回帰検査で担保(全生成面への全称主張はしない。qgb-design.md §3 注) |
| NF-04 | qgb の品質ゲートに接続し、判定は機械証跡 (gate.json) で説明可能 |

### クリア可能性担保の方式(F-02/F-03/NF-03 の実現)

- **収録 10 ステージ(生成選抜)**: 逆押し(pull)生成器で候補を多数生成し構成的に可解な面を作った上で、BFS ソルバーで全 10 面の可解性を機械検証。最短手数はソルバー出力をステージデータに焼き込み、テストで「焼き込み値 == ソルバー再計算値」を照合する(手書き値の混入を防ぐ。記録の真正性)。選抜の詳細は §7.1。
- **生成ステージ(ランダムモード)**: ゴール状態から逆押し(pull。合法 push の厳密な逆写像)による構成的保証に加え、固定シード代表集合(固定シード群 × 全難易度)のソルバー回帰検査で担保する(二重担保)。機械検査が示すのは代表集合上の全数通過であり、全生成面に対する全称主張はしない(qgb-design.md §3 注と同じ限定)。

## 2. 技術選定と制約

| 項目 | 選定 | 理由 |
|---|---|---|
| 実装言語 | vanilla JS (ES2022, ESM) | ユーザー選択。依存ゼロで審美的な UI を自作 |
| テスト | node:test + node:assert (Node 22 組込) | npm 依存を増やさない。`node --test` のみで完結 |
| 実行方法 | ローカル HTTP サーバ経由 | ESM は file:// で CORS 制限により動かない。`serve.ps1`(または `py -3 -m http.server`)を同梱 |
| ソルバー | 状態空間 BFS(移動単位)+ デッドロック枝刈り | 10 面規模(箱 ≤ 6、盤面 ≤ 12×10 目安)では BFS で十分。最短「歩数」が直接得られる |
| 生成器 | 逆押し生成 + シード付き PRNG (mulberry32) | 可解性の構成的保証。シード固定で決定論 → テスト可能 |
| UI 検証 | コアと UI の分離 + 構文検査 + 目視 | jsdom 等のテスト専用依存を増やさない(方針)。ロジックはすべてコア側に置く |

## 3. モジュール構成

```
index.html            # エントリ (script type="module")
styles.css            # 配色・レイアウト (絵文字グリッドの装飾)
serve.ps1             # ローカルサーバ起動 (Windows)
src/
  core/               # ★ DOM 非依存・純粋 ESM (node:test の対象)
    board.js          # 盤面モデル: テキスト形式のパース/シリアライズ/検証
    game.js           # ゲーム状態機械: 移動・押し・undo・リセット・勝利判定・歩数・リプレイログ
    solver.js         # BFS ソルバー: 可解性判定 + 最短歩数 + 解手順
    generator.js      # 逆押しステージ生成器 (シード付き)
    rng.js            # mulberry32 PRNG
    stages.js         # 生成選抜 10 ステージデータ (盤面テキスト + シード + パラメータ + ソルバー由来 minMoves を焼き込み。§7.1)
    progress.js       # クリア記録の純粋直列化 (serialize/deserialize/merge。DOM 非依存でテスト可能)
  ui/                 # DOM 依存層 (薄く保つ。ロジックを書かない)
    render.js         # 盤面 → DOM (固定サイズ CSS グリッドセル + 絵文字/破線枠)
    storage.js        # localStorage adapter (progress.js の薄い皮。直列化ロジックを持たない)
    app.js            # 画面遷移・キー入力・メニュー・リプレイ UI
tests/                # node:test (*.test.mjs)
tools/
  verify-stages.mjs   # 全ステージ可解性検証 CLI (qgb ゲート用、exit code + 証跡表出力)
  curate-stages.mjs   # 収録10ステージの選抜・焼き込み CLI (§7.1。実行すると src/core/stages.js を再生成)
  param-layers.mjs    # 候補生成レイヤのパラメータ表 (curate-stages.mjs / verify-stages.mjs 共用。§7.1)

.quality-system/      # qgb (別文書)
```

依存方向: `ui → core` の一方向のみ。`core` は `document`/`window` を参照しない。

## 4. 盤面テキスト形式

標準 Sokoban 記法を採用(コミュニティ互換):

| 文字 | 意味 |
|---|---|
| `#` | 壁 |
| ` ` (空白) | 床 |
| `@` | プレイヤー |
| `+` | プレイヤー (ゴール上) |
| `$` | 箱 |
| `*` | 箱 (ゴール上) |
| `.` | ゴール |

パース時の正規化(Codex 指摘: 境界条件の明示): 行長が不揃いの場合は最長行に合わせて**右側を床でパディングして矩形化**する。空行・使用不能文字は即エラー。

検証規則 (`board.js` の `validate()`):

1. プレイヤーがちょうど 1 人
2. 箱の数 == ゴールの数、かつ 1 個以上
3. **プレイヤーから到達可能な連結床領域**に全ての箱・ゴールがあり、その領域が壁で閉じている(flood fill が盤面外周に達しない)。到達不能な箱・ゴールは不合格
4. 使用可能文字のみで構成される
5. 既に全箱がゴール上(= 開始即クリア)の面は不正とする

## 5. コアロジック仕様 (game.js)

- **移動**: 上下左右 1 マス。移動先が壁なら不発(状態不変・歩数不変)。移動先が箱なら、箱のさらに先が床/ゴールのときのみ押して移動(箱 2 連続・壁は押せない)。
- **歩数 (moves)**: プレイヤーが実際に移動したら +1(押しも 1 歩)。不発は数えない。
- **undo**: 直前の 1 歩を巻き戻す(箱位置・プレイヤー位置・歩数・リプレイログすべて)。多段可。初期状態より前には戻れない。
- **リセット**: 初期状態に完全復帰。
- **勝利判定**: 全箱がゴール上。**勝利後は move・undo とも不発(状態不変)、reset のみ有効**(Codex 指摘: 境界挙動の明示)。
- **リプレイログ**: 有効だった移動を `U/D/L/R` の文字列で記録。undo はログ末尾を除去し、undo 後に別の手を指してもログは常に「初期状態から現在状態への再現手順」のみを保持する。

## 6. ソルバー仕様 (solver.js)

- 状態: `(プレイヤー位置, 箱位置集合)`。初期盤面から BFS(移動単位)。
- 返り値: `{ solvable: bool, minMoves: number|null, solution: "UDLR..."|null, stats }`
- **訪問済みキーの正規化**(Codex 指摘): 状態キーは `プレイヤー index + ":" + 箱 index を昇順ソートして結合`。箱の順序違いが別状態にならないことを保証する(キー生成関数はテスト対象としてエクスポートする)。
- 枝刈り:
  - 単純デッドロック: ゴール上でない箱が凹角(直交 2 方向が**静的壁 `#`**)に入った状態は展開しない。**箱や一時占有マスを壁扱いしない**(動的 corner 拡張は不健全になり得るため禁止。Codex 指摘)
  - 訪問済み状態集合
- 資源上限: 展開状態数上限 (既定 1,000,000) / 超過時は `{ solvable: null, reason: "limit" }` を返し、例外にしない。
- **規模上限の固定**(Codex 指摘: 移動単位 BFS の状態爆発対策): 担保対象ステージ(収録 10 面・生成面)は **箱 ≤ 5、盤面 ≤ 12×10** に制限し、この範囲で上限内・1 面 5 秒以内に収まることをテストで担保する(stages.test.mjs の規模上限テスト)。この上限を超える面が必要になった場合は push 単位探索 + プレイヤー到達可能性圧縮への移行を別途設計する(v0.1 スコープ外)。

## 7. 生成器仕様 (generator.js)

- 入力: `{ seed, width, height, boxCount, pullSteps, maxAttempts, minMovesFloor, wallDensity }`(難易度プリセット: easy/normal/hard が seed 以外を決める。maxAttempts 既定 100、minMovesFloor 既定 0、wallDensity 既定 0.16)
- **wallDensity**(テストプレイフィードバック対応、2026-07-11 追加): 部屋内部に配置する内壁の密度パラメータ(0〜0.45)。`generateConnectedRoom` が内部候補マスをシャッフルし、床連結性を flood fill で保証しながら `interiorArea * wallDensity` 枚を目標に内壁を追加する(連結性を壊す配置は棄却)。壁密度を上げるほど通路が曲がり、箱の押し方に制約が増える(易しすぎるという評価への対応の一部)。難易度プリセット別の値は本節末尾の表を参照。

### 構成的可解性保証の厳密定義(Codex 指摘 [Critical] への対応)

逆再生中に許す操作は、**forward の合法手の厳密な逆写像 2 種のみ**とする。テレポート・箱の任意再配置は禁止:

1. **逆歩行**: プレイヤーが隣接する床(壁・箱でない)へ 1 マス移動する。forward の歩行と同じ合法性判定(歩行は可逆)。
2. **pull**: プレイヤーが `p`、箱が `p+d` にあり、`p−d` が床(壁・箱でない)のとき、プレイヤーを `p−d` へ、箱を `p` へ動かす。これは合法 push「player `p−d`, box `p` → player `p`, box `p+d`」の厳密な逆写像である(pull 直後の状態から方向 `d` へ push すると pull 直前の状態に戻ることが確認できる)。

手順:

1. 外周壁 + ランダム内壁の部屋を生成(床連結性を flood fill で保証)
2. ゴール位置に箱を置いた「解けた状態」を作り、プレイヤーを箱以外の床にシードで配置(この位置が forward 解の終端位置になる)
3. 逆歩行と pull をシード由来の乱数で `pullSteps` 回分適用し、操作列を記録
4. 記録した操作列を**逆順に反転したものが forward 解**(pull ↔ push、歩行 ↔ 逆向き歩行)。生成器はこれを `solution`(`UDLR` 列)として返す
5. 最終状態を初期盤面として出力

**構成的保証の機械検証**: 生成器が返す `solution` を `applyMoves` で初期盤面に適用し勝利到達することをテストで確認する(保証が構成だけでなく実行で裏づけられる)。

### 終了保証と棄却(Codex 指摘 [Major] への対応)

- 棄却条件: ソルバーで `solvable !== true`(`null`=limit 超過も棄却) / `minMoves` が難易度別下限未満 / 箱が 1 個も動いていない / validate() 不合格 / **箱が 1 個もゴールから引き剥がされていない**(下記「全箱ゴール離脱」参照) / **初期盤面に `*`(箱 on ゴール)が 1 個でも残る**
- 棄却時は attempt 番号から決定論的に派生した子シードで再試行。**`maxAttempts` 回で打ち切り、明示エラー(`GeneratorError`)を投げる**(無限ループ・サイレント劣化をしない)
- 同一シード + 同一パラメータ → 同一ステージ(決定論)。

### 全箱ゴール離脱の二重保証(テストプレイフィードバック対応、2026-07-11 追加)

ユーザー評価「初めからゴールに入っている箱は不可(全部ゴールから動かせ)」への対応。逆押し生成は「ゴール状態(全箱がゴール上)」から出発するため、`pullSteps` 中に一部の箱しか引き剥がされないまま打ち切られると、初期盤面に箱 on ゴール(`*`)が残り得る。これを二重に防ぐ:

1. **構成保証(生成側)**: `buildCandidate` は未引き剥がしの箱 ID 集合 `unpulledBoxIds` を保持し、逆手候補のうち「まだ引き剥がしていない箱を pull する手」を優先プール(`priorityPulls`)として選ぶ。全箱が引き剥がされていれば通常の候補プールに戻る。結果を `movedAllBoxesFromGoals`(=`unpulledBoxIds.size === 0`)として候補に持たせる。
2. **棄却(検証側)**: `generateStage` は `candidate.movedAllBoxesFromGoals` が false、または `hasAnyBoxOnGoal(candidate.board)` が true の候補を明示的に棄却する。1 の構成保証が(`pullSteps` 不足等で)効かなかった場合の最終防波堤。
3. **テスト**: `tests/generator.test.mjs` の N-08(固定シード×全難易度プリセットで箱 on ゴールが 0 個、盤面テキストに `*` を含まない)、`tests/stages.test.mjs` の T-07(収録 10 面全てで同条件)で機械的に固定する。

補足(純度との関係、Codex レビュー 2026-07-11): 逆手候補の生成では「pull の結果、箱がゴールマスに着地する手」を候補から除外している。これは選択順序の偏りではなく**合法 pull 集合の意図的な部分集合**だが、採用する操作はすべて合法 push の逆写像のままなので構成的可解性保証(§7 冒頭)は損なわれない。到達可能なステージの多様性がわずかに狭まる(最短逆再生で箱を一時的にゴールへ置く必要がある面は生成されない)ことを許容するトレードオフである。

### 7.1 選抜(キュレーション)

収録 10 ステージ(F-02)は、生成器の候補群から機械チェックを通過したものを難易度カーブに沿って選抜し、`stages.js` に固定データとして焼き込む。実装は `tools/curate-stages.mjs`(選抜・焼き込み)+ `tools/param-layers.mjs`(候補生成レイヤのパラメータ表)+ `tools/verify-stages.mjs`(S3-solvability の代表集合検証)。

**第一ゴールとの関係**: 本プロジェクトの第一ゴールは「テストプレイ可能な状態」(収録 10 面 + ランダムモード + UI 操作一式が動くこと)であり、選抜された 10 面の面白さ・見た目の事前評価(見た目レポート等による人手選抜)は行わない。選抜の最終的な質はユーザーのテストプレイのフィードバックで詰め、必要な面の差し替えはデータ差し替えとして行う(下記「差し替え運用」)。**2026-07-11 のテストプレイ第 1 回で「クリアダイアログが早すぎる」「Hard 含め全体に非常にやさしい」というフィードバックを受け、本節はその対応版(難易度向上ラウンド)である。**

- **候補生成**: 逆押し生成器(本節冒頭の手順)を `tools/param-layers.mjs` の複数パラメータレイヤ(盤面サイズ・箱数・pullSteps・minMovesFloor・wallDensity の組。8 レイヤ)× マスターシード群(16 個、`maxAttempts=200`)で回し、候補を多数生成する。
- **品質チェック(候補に対する選抜時の機械チェック。`checkStageQuality` が実施。2 点)**:
  1. 焼き込み予定の `minMoves` がソルバー再計算値と一致すること(T-03 と同一の検証を選抜時にも適用)。
  2. **冗長な箱移動**の検出(`hasRedundantBoxMovement`): ソルバーが返す代表最短解 1 本を、初期箱位置で付与した箱 ID を保持したまま replay し、push された箱 ID ごとに占有マスの履歴を記録する。いずれかの箱が過去に占有したマスへ再び戻る push が 1 回でもあれば、その面は冗長な箱移動を含むとして選抜から棄却する。
  - この 2 点チェックに加えて、生成器自体が§7の全箱ゴール離脱・箱 on ゴール禁止を構成的に保証済みの候補のみを渡す(選抜側で再チェックしない。生成器の責務)。
  - 複雑な「面白さ」スコアリングは導入しないが、下記の**絡み合いスコア**は順位付け(tie-break)にのみ使い、通過/棄却の基準には使わない(品質チェックの本数は変えていない)。
- **絡み合いスコア(テストプレイフィードバック対応、2026-07-11 追加)**: `countBoxSwitches(board, solution)` が、代表最短解の中で「直前に押した箱と異なる箱を押す」回数(箱切替回数)を数える。同じ `minMoves` を持つ候補が複数あるとき、`compareCandidate` は箱切替回数が多い候補を優先する(1 本の最短解の中で複数の箱を交互に動かす必要がある面 = 箱同士の位置関係が絡み合っている面を優先し、「1 箱だけ黙々と押せば終わる」易しい構成を後退させる)。難易度そのものを直接操作するものではなく、同じ手数の中で相対的に手応えのある構成を選ぶための順位付け指標。
- **難易度カーブへの整列**: 通過した候補群からソルバー実測のスコア(`scoreMetrics`。§7.1 冒頭の各主軸指標の重み付き合成)を用いて 10 面を選び、ステージ番号に対し**厳密単調増加**になるよう並べる(2026-07-11〜12 のテストプレイ第4回フィードバックで「隣接逆転 1 箇所まで許容」から厳格化。判定基準は test-design.md T-04 と同一)。なお、焼き込み後の選抜結果が満たすべき不変条件(10 面・難易度単調・規模上限・ID 一意)は候補の品質チェックとは区別してテストで検査する(test-design.md Q-03)。

- **選抜の多様性制約(テストプレイ第4回フィードバック対応、2026-07-11〜12 追加)**: ユーザー指摘「stage08-10 はギミック相似で同じステージ、1-2 もそっくり、5 は 8-10 に似てる」への対応。`tools/curate-stages.mjs` の選抜 (`buildDiverseSequence`) は、難易度スコアの厳密単調増加(上記)に加えて以下を満たす組合せのみを採用する:
  1. **構造署名の一意性**: `structuralSignature`(minPushes・boxChanges・maxPhiBarrier・dependencyCount・dependencyDepth・mutualDependency・minGoalPushDegree・盤面サイズ・箱数のタプル)が収録 10 面内で重複しないこと。
  2. **policy(生成手筋)の分散**: `policyKey` が `scattered`(手筋なしの素の生成レイヤ)以外の値を取る場合、同一 policy は収録内で最大 2 回まで・隣接ステージでは同一不可。`scattered` は stage06 以降(上位帯)で最大 1 回まで(下位帯には制約を課さない)。
  3. **上位帯(stage07 以降)の隣接多様性**: 隣接する 2 面は `policyKey` が同一不可、かつ `upperFeelSignature`(箱数・mutualDependency の組)も同一不可。教訓: モチーフ(policy)名の分散だけでは体感の類似は防げない(stage05 と stage08-10 はモチーフが異なるにもかかわらず体感が同一だった。ユーザー指摘の直接原因)。箱数と相互依存の有無という「手触り」に近い属性まで揃えて初めて実効性を持つ。
  4. **スコアの厳密単調増加**(前項)。

  上記 1〜4 は総当たりのバックトラック探索 (`visit`) で満たす組合せを探す。制約と矛盾する場合は `curate-stages: diversity constraints conflict with rank/score constraints` で明示的に失敗する(条件を緩めて通す・サイレントに劣化させることはしない)。

  **限定事項**: 「似てる」の完全な機械化は本ラウンドでは未達である。構造署名一意性と policy 分散は機械的に検出できる相似性のみを排除するもので、それ以外の体感類似(配色・手筋の組合せ方の妙 等)は捉えきれない。最終判定は依然としてユーザーのテストプレイの目に置く(difficulty-theory.md §8 参照)。
- **難易度プリセットとの関係**: easy/normal/hard はランダムモードおよび候補生成時のパラメータセットであり、収録 10 面の難易度表示はステージ番号と minMoves カーブで決める(収録面はプリセットラベルを持たない)。

  難易度プリセット現行値(`src/core/generator.js` の `DIFFICULTY_PRESETS` が正。2026-07-11 難易度向上ラウンドで easy/normal/hard を一段引き上げ):

  | 難易度 | width×height | boxCount | pullSteps | minMovesFloor | wallDensity | maxAttempts |
  |---|---|---|---|---|---|---|
  | easy | 7×5 | 1 | 18 | 10 | 0.2 | 6000 |
  | normal | 9×7 | 3 | 42 | 20 | 0.2 | 2500 |
  | hard | 11×9 | 4 | 50 | 22 | 0.18 | 2500 |

  **目標未達の申し送り**: hard の当初目標は「12×10・floor32」だったが、この規模では BFS ソルバー(§6)による生成時の可解性検証・S3-solvability の代表集合検証の所要時間が実用範囲を超えるため、11×9・floor22 に妥協した(§10 開発体制の判断)。さらに難易度を上げるには、移動単位 BFS から push 単位ソルバー + プレイヤー到達可能性圧縮への移行(§6 に既述の「v0.1 スコープ外」の宿題)が前提になる。次に難易度を上げる際はこの移行を先に検討すること。

- **収録カーブの現状**: 2026-07-11 難易度向上ラウンド後の収録 10 面の `minMoves` は `4, 7, 10, 15, 17, 20, 22, 25, 27, 33`(stage01〜stage10)。stage10=33 が現在の上限であり、上記の BFS 制約により当面この値を大きく超える面は収録できない。
- **焼き込みデータ**: 各ステージは盤面テキスト・生成シード・生成パラメータ・ソルバー由来の最短手数(`minMoves`)を `stages.js` に静的データとして持つ。
- **焼き込み後の扱い**: T 系テスト(stages.test.mjs)・S3-solvability(qgb-design.md)による検証は、選抜方式の導入前と完全に同一の手順・同一のケースで行う。選抜方式の変更はデータの出自を変えるのみで、検証責務は変わらない。
- **差し替え運用**: 第一ゴール(テストプレイ可能な状態)達成後、ユーザーのテストプレイのフィードバックに基づき面を差し替える場合は、上記の選抜手順を経た新しい面でデータを差し替える(データ差し替えであり、検証手順自体の変更は伴わない)。2026-07-11 の難易度向上ラウンドもこの運用の一環(`tools/curate-stages.mjs` の再実行によるデータ差し替え)。

## 8. UI 仕様

### 画面

1. **タイトル/ステージ選択**: 10 ステージのカード(クリア済みマーク・自己ベスト歩数)+ ランダムモードカード(難易度選択)
2. **ゲーム画面**: 盤面(絵文字グリッド)、HUD(ステージ名 / 歩数 / 最短手数 / 自己ベスト)、操作ガイド
3. **クリアオーバーレイ**: 歩数 vs 最短手数、査定ランク(下記)、リプレイ再生ボタン、次のステージ / メニューへ

### 査定ランク(F-09。テストプレイ第4回フィードバック対応、2026-07-11/12 追加)

ユーザー要望「最短手に近いほど点が高い仕組み」への対応。`src/core/rank.js` の `computeRank(moves, minMoves)` が、クリア時の歩数を最短手数と比較して 4 段階の等級を返す。

- **等級と閾値**(`minMoves` を基準とした相対 + 絶対下限の併用。小さい `minMoves` でも A/B 帯が消えないようにするため):
  - **特 (S)**: `moves === minMoves`(最短ぴったり)
  - **優 (A)**: `moves <= minMoves + max(2, ceil(minMoves * 0.10))`
  - **良 (B)**: `moves <= minMoves + max(5, ceil(minMoves * 0.30))`
  - **可 (C)**: 上記以外(クリアはしているが最短からは離れている)
- **次の等級への案内**: 判定結果は `nextGrade`(現在より 1 段上の等級とその上限手数)を伴う。S 判定のときは `nextGrade: null`(これ以上の上位等級がない)。UI 側は「あと N 手で [上位等級]」の 1 行を表示する(ui-design.md §5.3.1)。
- **保存スキーマへの影響なし**: 等級は `bestMoves`(既存の localStorage スキーマ、§8 末尾)から都度導出する派生値であり、`progress.js` の保存データ構造は変更しない。
- **適用範囲**: 収録 10 ステージ・ランダム生成面のいずれもクリア時に同一ロジックで判定する(生成方式による特別扱いはない)。
- **UI 表示箇所**: クリアオーバーレイの査定印(スタンプ意匠)と次目標行、ステージ選択画面の棚カードにおける自己ベストの査定バッジ(視覚仕様は ui-design.md §5.3.1)。

## 9. リプレイ形式

- 記録: `U/D/L/R` の列(§5 リプレイログ)。クリア時に localStorage へ保存。
- 再生: 初期盤面からログを 1 手ずつ適用(タイマー駆動、等速/倍速)。再生ロジックは core の `game.js` を UI から呼ぶだけ(専用実装を持たない)。
- 検証: リプレイ文字列を適用して勝利状態に到達することをテストで保証(ソルバーの解もリプレイ形式で表現され、同一の適用関数を通る)。

## 10. 開発体制

- **Fable 5 (メイン)**: オーケストレーション指揮に徹する(意思決定・委任指示・受入判断・ユーザー対話)。手作業はしない。
- **作文系**(docs・REQ 本文・knowledge): Sonnet が執筆 → Codex がレビュー。
- **実装系**: Codex が実装 → Codex がレビュー(実装とは別セッション・敵対的プロンプト)+ Sonnet が異観点レビュー(仕様適合・テスト妥当性・層分離/API 契約)。
- **UI の視覚設計**: 視覚方針の決定・受入は Fable 5、具体的な視覚設計の成果物作成は Sonnet(frontend-design スキル使用)、実装は Codex。
- **qgb 機械操作・マイルストーン仕舞い**(テスト再実行 → コミット → プッシュ): Sonnet。
- **ユーザー**: 設計分岐の承認・テストプレイ(品質評価の最上位)。
- **レビュー収束**: Major/Critical は Fable 5 が裁定し Codex が修正、収束後に qgb ゲートへ進む。
- 品質ゲート: qgb (詳細は [qgb-design.md](qgb-design.md))
- マイルストーンごとに git commit/push で履歴を固定(qgb evidence の保存もコミットで行う)
