# REQ-SAVE-001: 保存記録の整合性と初期化操作の選択性

## 守りたい約束

保存された記録は参照先の盤面と常に整合し、初期化操作は宣言した範囲だけを消す(issue #1: 模範リプレイ・ランダム履歴・リセット2系統)。

具体的には以下がすべて成立する:

- v2 の保存記録は盤面ハッシュに紐付き、盤面が変わった記録だけを選択的に無効化する(全消去にしない)
- ランダム履歴は seed+params から再生成した盤面との整合を検証してから使う(不一致エントリは個別に除外する)
- 保存に失敗しても、既存データを意図的に破壊せず、失敗を利用者に伝える
- 「クリア記録の消去」と「完全初期化」は別の操作であり、消える範囲が異なる。特典(査定ランクの視聴済み上限)の解除は完全初期化のみが行う
- 模範解(`optimalSolution`)はソルバー由来の最短解であり、生成器の構成的証明解と混同しない
- v1 データ・保存キーは破壊しない(読まず、消さず、放置する)

## acceptance criteria(テストケース ID: SV-01〜SV-11)

以下のケース ID がすべて Green であること。ID は本 REQ で新設し、`tests/progress.test.mjs` 等の実装ファイルに対応させる(test-design.md §3.9 参照)。

| ID | 内容 |
|---|---|
| SV-01 | v2 の各ステージ記録は盤面ハッシュ(stage text の sha-256 等)を保持する。ロード時に現行 STAGES の盤面とハッシュ不一致の記録は**その記録だけ**無効化される(選択的失効)。他の記録・`solutionViewed`・ランダム履歴は保持される |
| SV-02 | ランダム履歴のエントリは seed+params から再生成した盤面と整合することを検証してから表示に使う。再生成失敗・不一致エントリは表示から除外され、他のエントリには影響しない |
| SV-03 | v1 データ・壊れた JSON・未知版のロードは安全に初期状態を返す(throw しない) |
| SV-04 | `setItem` が失敗した場合: (a) 失敗は呼び出し元(UI 層)へ返る (b) 書き込み前の既存保存データは意図的に消さず保持する (c) UI はユーザーに保存不能状態を表示する |
| SV-05 | `resetClearRecords`(クリア記録のみ消去)は `solutionViewed` を保持し、ランダム履歴の存在も保持する |
| SV-06 | `clearAllProgress`(完全初期化)はクリア記録・`solutionViewed`・ランダム履歴のすべてを消去する |
| SV-07 | 査定ランクの上限規則: `solutionViewed === true` の面(収録面・ランダム面いずれも)は最短手数でも `grade: "A"` かつ `cappedByViewing: true` を返す。`solutionViewed === false` の面は最短手数で `grade: "S"`(特)を返す。特典の解除は `clearAllProgress` のみで、`resetClearRecords` では解除されない |
| SV-08 | `optimalSolution`(収録面・ランダム面プールの両方)は初期盤面に適用すると勝利到達し、その手順長はソルバー再計算 `minMoves` と一致する(ソルバー由来の最短解であることの検証。生成器の構成的証明解とは別物) |
| SV-09 | 保存キーは `qgb-soukoban/v2` を使う。旧 v1 キーは読み込み処理からアクセスされず、削除処理の対象にもならない(コード上・テスト上の両面で確認) |
| SV-10 | 確認 UX: `resetClearRecords` は確認 1 段。`clearAllProgress` は確認 2 段階で、いずれかの段の文言に「模範解の視聴履歴・ランダム履歴も削除します」を含む |
| SV-11 | `mergeClearRecord` / `recordRandomPlay` は呼び出し前後で `solutionViewed` の値を変えない(既存フラグを保持したまま該当フィールドのみ更新する) |

注: v2 以降の版移行を無損失で行うことは将来の約束であり、今回のスコープ外(v1→v2 の移行処理は実装しない。破棄してよいとするユーザー判断済み)。

## 関連する段階と理由

| 段階 | 理由 |
|---|---|
| S1-static | 保存・査定ロジックのモジュールが構文検査に合格しなければ後続の検証が実行不能なため前提として必須 |
| S2-unit | 盤面ハッシュ整合・選択的失効・リセット2系統・保存失敗時の意味論・確認 UX の文言は、いずれも決定論的な入出力を持つロジックとして単体テストで検証できる |

S3-solvability(可解性証跡)・S4-artifact(配布物整合)は本 REQ の対象外。模範解の真正性検証(SV-08 相当)は REQ-SOLV-001 の S3(`tools/verify-stages.mjs`)にも収録面・シードプールの監査証跡として重複実装される(単一責任: 本 REQ は「記録として保存された `optimalSolution` の真正性」を単体テストで、REQ-SOLV-001 は「収録・生成データそのものの真正性」を独立スクリプトの証跡で担保する)。

## 限定(P5)

ALLOW は SV-01〜SV-11 が機械検査に通過したことのみを意味する。実際の localStorage 実装依存の挙動(ブラウザ間の容量制限差・プライベートモードでの `setItem` 失敗挙動の違い等)は単体テストのモック環境での検証に限定され、全ブラウザでの動作保証を意味しない。
